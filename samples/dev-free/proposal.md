# Proposal draft: Request for Proposal: Electronic Signature Service

Status: UNREVIEWED_DRAFT. Every requirement below quotes the RFP, and a person must review this draft before anyone relies on it.

## Our understanding of the College's needs

The College needs proposals submitted as a single PDF of no more than 20 pages through the procurement portal by 2026-12-01 12:00 UTC [REQ-0009]. The service must integrate with the College's student records system through its existing REST API [REQ-0018] and be live for students by 2027-01-11, the first day of spring enrollment [REQ-0023]. The Supplier must also keep an audit record of every signature event [REQ-0012], support current desktop and mobile browsers [REQ-0013], send reminders to signers who have not signed within 72 hours [REQ-0014], store signed documents for ten years [REQ-0016], and provide 99.5% availability in each calendar month excluding planned maintenance announced five working days in advance [REQ-0020]. Furthermore, the Supplier should provide templates for the twelve most used forms [REQ-0015], migrate signed records by 2027-02-28 [REQ-0017], and respond to severity-one incidents within one hour [REQ-0021]. Bidders may propose an on-premises deployment option [REQ-0019].

## How we would deliver

We would assemble the proposal as a single PDF of at most 20 pages and submit it through the College's procurement portal by 2026-12-01 12:00 UTC [APP-001]. The order of submission is an assumption to ensure compliance [APP-001]. We would ensure the service is live for students by 2027-01-11, the first day of spring enrollment, integrating with the College's student records system through its existing REST API [APP-001]. We would keep an audit record of every signature event, including the signer's identity, the time, and the document version, and store signed documents for ten years [APP-002]. The underlying storage medium is an assumption [APP-002]. We would support signing on current desktop and mobile browsers, and send a reminder to each signer who has not signed within 72 hours [APP-003]. The reminder delivery channel is an assumption [APP-003]. We would maintain service availability of 99.5% of the time in each calendar month, excluding planned maintenance announced five working days in advance [APP-004].

## Risks and assumptions

The main risks include the final document exceeding 20 pages or portal congestion delaying the 2026-12-01 12:00 UTC upload, which risks instant disqualification [RSK-001]. We enforce an 18-page budget immediately and perform a dry-run upload one week before the deadline [RSK-001]. Integration complexities with the College's student records system REST API could delay go-live past 2027-01-11 and disrupt spring enrollment [RSK-002]. We request API documentation and sandbox access prior to contract award and build a mock API server [RSK-002]. Pulling resources for spring support could cause migration to slip past 2027-02-28 and trap historical signed records [RSK-003]. We allocate dedicated data engineering resources and define a prioritized batch migration schedule [RSK-003]. Open questions remain regarding form templates, migration data volumes, optional on-premises pricing, severity-one support channels, webhook support versus polling, and the current tool's data format and schema [Q-01, Q-02, Q-03, Q-04, Q-05, Q-06].
